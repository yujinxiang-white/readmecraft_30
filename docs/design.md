# 设计说明

## 目标与非目标

目标：让一个仓库的 README 是否「可上手」变成可执行、可讨论的判断。
非目标：评价文字质量、检查 Markdown 语法（那是 markdownlint 的职责）、生成完整官网。

## 为什么规则是数据

`rules.py` 里每条规则是一个 `Rule` 数据类实例，判定函数放在 `scorer.py` 的 `CHECKS` 字典中。
这样做的好处是：

1. 权重调整只改一行，不会牵动 CLI 与渲染层；
2. 新增规则时，规则表、README 表格、JSON 输出自动同步；
3. 单元测试可以只针对单条规则，定位失败原因快。

## 评分模型

八条规则权重合计 100：标题 15、简介 10、安装 15、使用 15、许可证 15、贡献 10、徽章 10、目录 10。
选择加权而不是平均分，是因为「安装」与「使用」直接决定访客能否跑起来，理应占更高权重。

等级划分：A ≥ 90、B ≥ 75、C ≥ 60、D < 60，60 分同时作为 CLI 退出码的阈值。

## 已知取舍

- 规则基于正则与标题文本匹配，宁可漏判也不误判，例如不检查小节内文字是否为空；
- 不解析 HTML 与前端框架组件；
- 中文标题与英文标题同时支持，但别名表需要人工维护，新增语言需提 Issue。
